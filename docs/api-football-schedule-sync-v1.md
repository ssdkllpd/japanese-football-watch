# Pre-match schedule synchronization v1

The schedule workflow starts disabled. Manual `preview` reads D1 and the provider and uploads a plan, without modifying D1, R2, or the Admin Worker. A manual `execute` requires `RUN SCHEDULE SYNC`; the daily 01:37 UTC trigger additionally requires `API_FOOTBALL_SCHEDULE_SYNC_ENABLED=true`. Do not enable the repository variable before inspecting the first full-season preview and deployment readiness.

Each run requests all ten reviewed 2026 seasons once (ten charged fixture requests, plus the quota-free status request). The complete provider fixture ID set must include every stored ID, pages must be complete, and the provider quota must leave the 100-request reserve. A partial response cannot delete or move stored fixtures. The plan holds new IDs, published details, and non-schedule statuses for separate reconciliation. A preview reports every candidate and marks more than 20 as requiring multiple batches; normal execution processes at most 20 changes, leaving the rest for subsequent scans. The 20 changes are schedule headers, separate from the fixture detail publication ledger. An explicitly pinned initial catch-up can process all reviewed changes while checking Paid D1 capacity every 20 fixtures.

Only unpublished `NS`, `PST`, or `TBD` fixtures are eligible. The Admin Worker checks the old kickoff, old status, fixture/league/season identity, and absent published revision before changing the kickoff or status. A provider `PST`/`TBD` kickoff is considered unconfirmed; D1 retains the last confirmed kickoff as an internal historical value while the UI renders `日程未定`. Once the provider returns `NS` with a new kickoff, it can move to the new JST date. Until then the postponed fixture remains associated with its previous date in date feeds, visibly marked as undetermined; a dedicated undated-fixtures listing is outside this unit.

The D1 update atomically stores a pending date-index repair. The next Admin operation rebuilds the old and new generic and competition R2 indexes, validates D1 coverage, then clears the pending record. If publication stops, the next execute first drains pending repairs, before reading the D1 inventory or fetching provider data. A second change is refused until that repair is complete. The workflow uses the shared staging writer group, the reviewed target check, and the Paid D1 usage guard. Existing rich fixture bundles and their corrections are never replaced by schedule metadata.

After merge, run `API-Football Schedule Sync` with `mode=preview`, inspect `schedule-sync-<run>` for `changes`, `held`, `scanned`, and quota, and compare sampled changes with the D1 dates. Enable execution only after an independently checked preview. The normal 15-minute fixture automation remains separately gated and disabled.
