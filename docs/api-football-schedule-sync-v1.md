# Pre-match schedule synchronization v1

Execution remains disabled until independent review, deployment and live-data validation are complete. Bounded catch-up scheduled writes were paused on main in commit `4fcf96d61c84450e9e13bdbe51fae1e67283008e`. Manual catch-up preview remains available.

The schedule workflow scans ten configured 2026 seasons every four hours (01:37, 05:37, 09:37, 13:37, 17:37 and 21:37 UTC), behind `API_FOOTBALL_SCHEDULE_SYNC_ENABLED=true`. Manual preview reads D1 and the provider without publishing. Execute requires `RUN SCHEDULE SYNC` and the Admin publish gate. Six scans consume 60 fixture-discovery requests per day, plus quota-free status calls. The provider reserve remains 100 requests. This is periodic pre-match checking; changes immediately before kickoff may wait for the next scan.

Each scan requires complete, non-empty, single-page provider seasons and a valid D1 inventory with its exact window count. There is no 3000-row minimum. The configured policy deliberately retains the reviewed ten-league 2026 scope; a season rollover requires coordinated policy, target and review updates. Missing provider IDs are held with their stored values rather than deleted. New IDs require catalog reconciliation. Published details are held with the exact stored/provider kickoff and status differences. The run summary exposes these holds with a warning; they are not counted as resolved.

Unpublished NS/PST/TBD/CANC/ABD/AWD/WO/SUSP/INT headers can be updated. Final detail states and live play are handled separately. PST/TBD retain the last confirmed kickoff until the provider confirms a new NS kickoff; the club screen lists them under upcoming, with the time marked undetermined. A dedicated undated listing is outside this change.

Normal execution processes at most 20 schedule headers even if the full plan has more than 240 changes. The priority uses the nearer of the old and new confirmed kickoffs, with ID only as a tie breaker. An explicit `--all` catch-up remains capped at 240 and checks account usage every 20 headers. Detail publication has its separate daily ledger.

Migration `0010_d1_schedule_repair_token.sql` must be applied before deploying the revised Admin Worker. It adds a token column with an empty default so existing repair rows can still be drained. Each new update reserves the single repair slot inside the D1 transaction, using the exact old header, scope and unpublished state. Its conditional fixture update requires the same unique token. A stale or occupied slot modifies neither table; batch results must show one insert and one update. Repair rebuilds both date indexes and their coverage, then deletes only its own token. Published results on the destination date can be repaired. Fixture publication drains its pending schedule repair first; an R2 failure stops publication before changing the D1 fixture.

Active staging writer workflows use `d1-staging-write` with `queue: max` and `cancel-in-progress: false`. GitHub permits at most 100 waiting jobs in that group, so it remains a finite queue. Completed push-triggered one-off rollout files are deliberately unchanged to avoid another rollout on merge.

The 15-minute result automation reads current D1 dates before planning and declares `previousDateJst` when the fetched result crosses a JST date. Kickoff corrections do not change fixture identity. Artifact reconciliation quarantines individual failed fixtures; Admin publication and date refresh run as a separate verified unit for each ready fixture. Only verified fixture and standings identities advance durable state. Partial failures leave the run visibly failed after the verified subset is saved.

After schedule execution, the audit compares selected headers with the pre-write plan, verifies every unselected/held header against the full pre-write D1 inventory, compares affected generic and competition R2 payloads with all-competition D1 rows (including outside-policy fixtures), checks coverage digests and zero pending rows, and samples both public read routes. A second ending inventory detects changes during collection. All input/output JSON is retained as evidence. These are checks of the declared update and stored/public data; they do not independently prove provider freshness or browser UI behavior. An unavailable public read makes the audit incomplete rather than PASS.

The account usage guard checks trailing-31-day D1 rows written against 40M and rows read against 20B. It is called before schedule writes and before the 15-minute workflow's first writes. It does not establish a total-bill ceiling: R2 operations, Worker CPU/requests, storage, billing-period boundaries and analytics delay need separate monitoring.

## Recovery and enablement

1. Keep both automatic-update gates disabled. Read the live SQL checks and preserve the evidence before changing any pending rows. Never delete a checkpoint merely to unblock the job.
2. After independent review and merge, apply migration 0010 and deploy the Admin Worker through the staging provisioning workflow. Drain pending repairs through the protected `fixture_schedule_repair` operation; retry an interrupted R2 write. If the stored fixture is missing or differs from the checkpoint destination, stop and investigate the full fixture/revision/R2 history.
3. Run a fresh schedule preview. Inspect missing/new/published holds and their exact differences. Published fixtures require detail reconciliation that preserves overrides and explicitly declares any old date; they must not pass through the schedule-header updater. Fixture 1552141 remains unverified until its live header, canonical R2 bundle and provider difference are available.
4. Run one bounded execute with the full audit and read both old/new generic and competition feeds in the browser. A failed Worker sample or pending row blocks enablement. The September 30 rollout's earlier D1 date-only artifact does not prove its kickoff/status/R2/held preservation.
5. Enable schedule checking first, then result automation only after its result/date-relocation preview and live validation succeed. Re-enable catch-up only if still needed and independently reviewed.
