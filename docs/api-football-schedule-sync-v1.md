# Pre-match schedule synchronization v1

Execution remains disabled until independent review, deployment and live-data validation are complete. Bounded catch-up scheduled writes were paused on main in commit `4fcf96d61c84450e9e13bdbe51fae1e67283008e`. Manual catch-up preview remains available.

The schedule workflow scans ten configured 2026 seasons every four hours (01:37, 05:37, 09:37, 13:37, 17:37 and 21:37 UTC), behind `API_FOOTBALL_SCHEDULE_SYNC_ENABLED=true`. Manual preview reads D1 and the provider without publishing. Execute requires `RUN SCHEDULE SYNC` and the Admin publish gate. Six scans consume 60 fixture-discovery requests per day, plus quota-free status calls. The provider reserve remains 100 requests. This is periodic pre-match checking; changes immediately before kickoff may wait for the next scan.

Each scan requires complete, non-empty, single-page provider seasons and a valid D1 inventory with its exact window count. There is no 3000-row minimum. The configured policy deliberately retains the reviewed ten-league 2026 scope; a season rollover requires coordinated policy, target and review updates. A small number of missing provider IDs are held with their stored values rather than deleted. If a season loses more than max(2, floor(stored count × 5%)) IDs, discovery stops before writes because the response may be partial. New IDs require catalog reconciliation. Published details are held with the exact stored/provider kickoff and status differences. The run summary exposes these holds with a warning; they are not counted as resolved.

Unpublished NS/PST/TBD/CANC/ABD/AWD/WO/SUSP/INT headers can be updated. Final detail states and live play are handled separately. PST/TBD retain the last confirmed kickoff until the provider confirms a new NS kickoff; the club screen lists them under upcoming, with the time marked undetermined. A dedicated undated listing is outside this change.

Normal execution processes at most 20 schedule headers even if the full plan has more than 240 changes. Priority uses the nearest future old/new confirmed kickoff, with past-only changes after future changes and ID only as a tie breaker. The planner takes an explicit clock for deterministic tests. An explicit `--all` catch-up remains capped at 240 and checks account usage every 20 headers. Detail publication has its separate daily ledger.

Migrations `0010_d1_schedule_repair_token.sql` , `0011_d1_date_repair_journal.sql` and `0012_d1_date_repair_control.sql` must be applied before deploying the revised Workers. Each schedule update reserves a token in the same D1 transaction as its conditional header update. Success is checked against the stored header and token; D1 `meta.changes` includes trigger writes and is not an exact one-row count. Repair deletes only its own token. A legacy checkpoint can repair the old date, declared destination and current date even when another header writer moved the fixture again.

Migration 0011 journals old/new dates on header and publication changes. The unfinished date/competition scopes remain durable even if an interrupted repair has already replaced the generic R2 index and deleted coverage. `fixture_schedule_repair` registers all old/intermediate/current scopes for a legacy fixture checkpoint, then repairs one date per request and deletes the checkpoint only when those dates are drained. Without a legacy checkpoint it repairs one journaled date per request. Competition scope writes and empty-competition reads are batched, with a reviewed maximum of 24 competition indexes per date. It can remove a known relocated fixture from its former index; unknown orphan R2 IDs still stop repair. Every R2 attempt saves a generation token, re-reads D1 after writing and clears only its own token. A stale or failed attempt that reaches its post-write check leaves retry work. A stale writer terminated between its R2 write and that check can leave stale R2 with an empty journal; see the SCHED-R3 reconciliation runbook. D1/R2 writes are not atomic.

The automation client drains only the fixture’s owned old/intermediate/current and declared refresh dates through separate Admin invocations before each result publication. A global initial sweep attempts each date independently, records failed dates and continues healthy work. Its incomplete report still makes the workflow visibly fail after verified work is saved. Publication refuses a pre-existing fixture checkpoint with a retryable 409; the client drains and retries that specific response. Repairs are not inlined into the publication's 50-query budget. The fixture journal also covers a schedule write that races after the publication preflight. Failed repairs leave the fixture unpublished when they occur before that publication.

Active staging writer workflows use `d1-staging-write` with `queue: max` and `cancel-in-progress: false`. GitHub permits at most 100 waiting jobs in that group, so it remains a finite queue. Completed push-triggered one-off rollout files are deliberately unchanged to avoid another rollout on merge.

The 15-minute result automation reads current D1 dates before planning and declares `previousDateJst` when the fetched result crosses a JST date. Kickoff corrections do not change fixture identity. Fetch, artifact binding and R2 reconciliation quarantine individual failed fixtures; Admin publication and date refresh run as a separate verified unit for each ready fixture. Only verified fixture and standings identities advance durable state. Partial failures leave the run visibly failed after the verified subset is saved.

After schedule execution, the audit compares selected headers with the pre-write plan, verifies every unselected/held header against the full pre-write D1 inventory, compares affected generic and competition R2 payloads with all-competition D1 rows (including outside-policy fixtures), checks coverage digests and requires no pending repairs for the changed fixtures or affected dates, and samples both public read routes using `?fresh=1`. Unrelated repair checkpoints and dates are reported with initial/final evidence while the affected scopes still undergo every comparison. A completed report has `passed:true` for those scopes and `overallPassed:false` when isolated repairs were observed; the capture CLI saves that report and exits 1, keeping the workflow visibly failed. See [the SCHED-R4 response](schedule-review-r4-fix-20261008.md). Fresh reads require the dedicated `PUBLIC_DATE_AUDIT_TOKEN` secret (at least 32 characters) in `x-jfw-audit-token`, skip the date cache and return `no-store`, retaining the existing origin and rate-limit checks; normal visitors retain the 300-second cache. The audit independently compares status, team, score and the top-level competition header (including empty feeds) with D1, applying active fixture corrections in the same deterministic order as the public projection. A second ending inventory detects changes during collection. All input/output JSON is retained as evidence. These are checks of the declared update and stored/public data; they do not independently prove provider freshness or browser UI behavior. An unavailable public read makes the audit incomplete rather than PASS.

The account usage guard checks trailing-31-day D1 rows written against 40M and rows read against 20B. It is called before schedule writes and before the 15-minute workflow's first writes. It does not establish a total-bill ceiling: R2 operations, Worker CPU/requests, storage, billing-period boundaries and analytics delay need separate monitoring.

## Recovery and enablement

1. Keep both automatic-update gates disabled. Read the live SQL checks and preserve the evidence before changing any pending rows. Never delete a checkpoint merely to unblock the job.
2. Before merge, keep automatic updates disabled and configure `PUBLIC_DATE_AUDIT_TOKEN` (a random secret of at least 32 characters) in the GitHub `d1-staging` environment alongside the existing Cloudflare, Admin and provider secrets. After independent review and the merge decision, `Deploy Public Worker` runs a local prerequisite check, calls the same-commit staging provision workflow to apply migrations 0010–0012 and deploy/check the Admin Worker, then deploys the public Worker and installs that same audit secret. Failure or cancellation of either prerequisite job prevents public deployment. Both authenticated fresh date routes must pass the public deployment checks. Do not rerun a deployment from an older commit; use the reviewed merged commit. A standalone `D1 Staging Provision` deploys only the Admin Worker and does not complete this rollout. See [the deployment runbook](schedule-deployment-order-20261008.md). Drain pending repairs through the protected `fixture_schedule_repair` operation; retry an interrupted R2 write. A checkpoint destination that differs from the current date is repaired through all three dates. If the fixture is missing or has an invalid published revision, stop and investigate its full history. Do not manually clear the journal.
3. Run a fresh schedule preview. Inspect missing/new/published holds and their exact differences. Published fixtures require detail reconciliation that preserves overrides and explicitly declares any old date; they must not pass through the schedule-header updater. Fixture 1552141 remains unverified until its live header, canonical R2 bundle and provider difference are available.
4. Run one bounded execute with the full audit and read both old/new generic and competition feeds in the browser. A failed Worker sample or pending row blocks enablement. The September 30 rollout's earlier D1 date-only artifact does not prove its kickoff/status/R2/held preservation.
5. Enable schedule checking first, then result automation only after its result/date-relocation preview and live validation succeed. Re-enable catch-up only if still needed and independently reviewed.

## SCHED-R3 recovery and consistency limits

See [the SCHED-R3 fix and recovery runbook](schedule-review-r3-fix-20261008.md). Protected status, enqueue and evidence-bound authorization operations support investigating a failed date without deleting its journal. Verified empty historical competition scopes are excluded from future repair budgets; unfinished scopes remain until verified. Ordinary UTC kickoffs stored without milliseconds are normalized in date feeds.
