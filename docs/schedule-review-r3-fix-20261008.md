## 修復の境界

`fixture_schedule_repair_status` は残日付・世代トークン・最終エラーを返します。`dates`（最大6日付）と `fixtureId` で関連する日付だけを取得できます。全体排出は1日付につき1回試し、失敗日付を除外して次へ進み、最大100回で終了します。最後に除外なしで残件数を照合するので、失敗日付を完了と扱いません。直接の `repair` CLIは未完了ならexit 1です。

両workflowの最初の排出だけ `--continue-on-error --report FILE` を使います。データ不整合があっても健全な試合を実行し、報告を保存して最後のstepで未完了を失敗表示します。HTTP／資格情報／予算エラーは全体を止めます。試合自身または移動元・移動先の修復に失敗した場合、その試合は成功件数に含めません。結果公開の旧・新日付関連付けはmigration 0012のtriggerで保持し、途中で計画が作り直されても旧日付を失いません。

修復は1回のAdmin呼出しにつき1日付です。1日付最大24大会と、同日付に重なる最大20旧checkpointの上限は残ります。未完了の大会スコープは保持し、修復に成功した空の過去大会スコープだけを次回の候補から外します。

## 調査済み日付の復旧

すべての操作は既存Admin endpointと `ADMIN_INGEST_TOKEN` を必要とします。キューやcheckpointをSQLで削除して進めないでください。

1. `fixture_schedule_repair_status` で失敗日付と `repair_token` を読み、D1の試合一覧・大会・日付・有効な公開revisionを確認します。
2. 該当日の汎用R2オブジェクトをバイト列として保存しSHA-256を計算します。孤児IDは全D1で不在を確認します。旧契約／破損JSONの置換を許可する場合もD1を正としてよい根拠を記録します。
3. 下の形式をJSONファイルに保存し、`node scripts/d1/resolve-date-repair.mjs reviewed-repair.json` を実行します。スクリプトは承認後にその日付だけを排出し、未完了ならexit 1です。実行にはAdmin URLとtokenを環境変数で渡します。

```json
{
  "schemaVersion": "jfw-d1-admin-ingest/1",
  "operation": "date_index_repair_authorize",
  "date": "2026-12-01",
  "expectedRepairToken": "statusから取得した現在のtoken",
  "sourceSha256": "現在の汎用R2本文の64桁SHA-256",
  "orphanFixtureIds": ["af:fixture:99999"],
  "allowInvalidPrevious": false,
  "reason": "D1全件と過去の公開履歴を照合して孤児であると確認した根拠"
}
```

承認時にtoken、R2ハッシュ、孤児のD1不在、R2内のIDを検証します。破損JSONには `allowInvalidPrevious:true` が必要です。破損JSONからID証跡を読めない場合は孤児リストを空にします。原本はR2の `audit/date-repair/<date>/<sha>.json` に保存し、理由・ハッシュ・保管keyをD1に保持します。承認自体ではキューを消しません。再構築も同じハッシュの証跡に限定し、孤児がD1へ戻った場合は拒否します。R2内容が変化した場合は新たに調査してください。

## 強制終了時の限界と再照合

旧writerがR2へ古い一覧を書き、その直後に後検証を実行できず終了し、別writerが新世代のキューを既に消していた場合、**古いR2と空キューが残り得ます**。キューが空という事実だけではD1/R2一致を証明できません。元G3の競合はこの限界を示し、今回のトークン方式もR2への原子的な条件付き書込みを提供しません。従来文書の無条件の「最終一致を保証」はこの条件には適用しません。

運用者は書込みの同時実行を直列化し、取消・強制終了後の影響日付と、定期的に対象期間のD1/R2を再照合してください。通常の公開レスポンスはD1や300秒キャッシュを使うため、それだけでR2の原本一致を判断しないでください。差分があれば次のJSONを保存して `resolve-date-repair.mjs` に渡します。

```json
{
  "schemaVersion": "jfw-d1-admin-ingest/1",
  "operation": "date_index_repair_enqueue",
  "date": "2026-12-01",
  "reason": "中断された並行writerの影響日付を再照合しD1とR2の差分を確認"
}
```

この操作は新しい世代の修復を登録してから対象日を再構築します。完了後は汎用／大会別R2本文、D1一覧、coverage、認証したfresh公開読取りを比較してください。自動的な定期再照合のschedulerは今回追加・有効化していません。したがって強制終了ケースの無人回復も保証しません。
